## Choix des features

Les features utilisées capturent le **contexte du passage** sans inclure les horaires bruts :

| Feature | Type | Description |
|---------|------|-------------|
| `nom_ligne` | Catégorielle | Ligne de transport (RER A, Tram T9…) |
| `jour_semaine` | Catégorielle | Jour de la semaine (lundi…dimanche) |
| `periode_journee` | Catégorielle | Tranche horaire (pointe_matin, creuse_matin…) |
| `meteo` | Catégorielle | Météo Paris ce jour (pluie_legere, degage…) |
| `heure_tranche` | Numérique | Heure de l'horaire prévu (0–23) |
| `mois` | Numérique | Mois de l'année (1–12) |
| `jour_ferie` | Numérique | 1 si jour férié ou dimanche, 0 sinon |
| `occupation` | Numérique | Entrées/heure à l'arrêt (open data IDFM) |

> **Pourquoi `horaire_arrivee_estime` et `horaire_arrivee_prevu` ne sont PAS des features ?**
> Ces deux colonnes servent uniquement à calculer la cible `retard_sec = estime − prevu`.
> Les inclure comme features serait de la **fuite de données** (*data leakage*) :
> le modèle aurait accès à la réponse pendant l'entraînement et serait inutilisable en production
> (on ne connaît pas `horaire_arrivee_estime` avant que le train soit en route).
> L'information temporelle utile est capturée via `heure_tranche`, `periode_journee` et `mois`.

---

## Pipeline de préparation

1. **Calcul de la cible** — `retard_sec = horaire_arrivee_estime − horaire_arrivee_prevu` (en secondes)
2. **Filtrage** — suppression des lignes où la cible n'est pas calculable (`dropna`)
3. **Encodage catégoriel** — `pandas Categorical.cat.codes` (pas de sklearn, pas de fuite entre train/test)
4. **Imputation features numériques** — NaN remplacés par la moyenne de la colonne (dataset corrigé)
5. **Split** — 80 % entraînement / 20 % test fixe (`random_state=42`)

> Toutes les chaînes de caractères catégorielles sont normalisées en **minuscules sans accents**
> (`pointe_matin`, `pluie_legere`, `lundi`…) pour garantir des jointures et encodages reproductibles.

---

## Hyperparamètres optimisés

Pour chaque modèle disposant d'une grille, un `GridSearchCV(cv=3, scoring='r2')` est lancé
dans un **process séparé** (n_jobs=1 interne pour éviter les processus imbriqués).
Les meilleurs paramètres sont mis en **cache JSON** (`resultats_modeles/best_params.json`)
— au prochain run, le GridSearch est sauté et les params sont relus depuis le cache.

| Modèle | Paramètres explorés |
|--------|---------------------|
| Ridge | `alpha` |
| DecisionTree | `max_depth` (borné, pas de None), `min_samples_split`, `min_samples_leaf` |
| RandomForest | `n_estimators`, `max_depth` (borné), `min_samples_leaf` |
| ExtraTrees | `n_estimators`, `max_depth` (borné), `min_samples_leaf` |
| GradientBoosting | `n_estimators`, `learning_rate`, `max_depth` |
| HistGradientBoosting | `max_iter`, `learning_rate`, `max_leaf_nodes`, `l2_regularization` |
| KNeighbors | `n_neighbors`, `weights` |

> `max_depth=None` est **exclu** de toutes les grilles sauf HistGBM.
> Un arbre sans limite de profondeur mémorise les données d'entraînement (overfitting).
> HistGBM se régularise autrement via `max_leaf_nodes` et `l2_regularization`.

## Glossaire des métriques

| Métrique | Formule | Interprétation | Limite |
|----------|---------|----------------|--------|
| **R²** | `1 − SS_res/SS_tot` | Part de variance expliquée. 1=parfait, 0=prédit la moyenne. | Trompeur si peu de variance dans la cible (beaucoup de retard≈0). |
| **MAE** | `mean(|y−ŷ|)` | Erreur absolue moyenne en secondes. | Toutes les erreurs ont le même poids, insensible aux outliers. |
| **RMSE** | `√mean((y−ŷ)²)` | Erreur quadratique. Amplifie les grandes erreurs. | Sensible aux prédictions très éloignées. |
| **MAPE** | `mean(|y−ŷ|/y)×100` | Erreur relative en %. | **Instable** si retard réel ≈ 0 (division par ~0). |
| **Proche≤60s** | `mean(|y−ŷ|≤60)×100` | % de prédictions à ±60s de la réalité. | Métrique la plus fiable sur ce dataset. |
